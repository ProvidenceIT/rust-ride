## 2026-01-03 - Subtask 1.4 Complete: Auto-Reconnect Logic

### Completed:
- Added `auto_reconnect` and `reconnect_delay_ms` config options to `HidConfig`
- Added `DeviceReconnected` event type for auto-reconnect notifications
- Added `auto_reconnect_targets` HashMap to track devices that should be auto-reconnected
- Implemented `track_for_reconnect()` and `untrack_for_reconnect()` methods
- Modified `open_device()` to automatically track devices for reconnect
- Modified `close_device()` to remove devices from reconnect tracking (user explicitly closed)
- Updated monitoring loop to detect returning devices and auto-reconnect them
- Added configurable delay before reconnect attempt (default 1 second)
- Added unit tests for reconnect tracking and config

### Auto-Reconnect Flow:
1. When user opens a device via `open_device()`, it's tracked by identity key
2. If device is unplugged, it remains tracked for reconnection
3. When device is replugged and detected in monitoring loop:
   - Check if it's in reconnect targets
   - Wait for configured delay (default 1 second)
   - Attempt to reopen the device
   - Emit `DeviceReconnected` event on success
4. If user explicitly calls `close_device()`, device is removed from tracking

## 2026-01-03 - Subtask 2.1 Complete: HID Input Reading Task

### Completed:
- Created new `src/hid/input.rs` module with `HidInputReader` struct
- Implemented background task that reads input reports from open HID devices
- Uses non-blocking `read_timeout()` for responsive input reading
- Handles multiple devices concurrently using `spawn_blocking` for hidapi operations
- Created `HidDeviceType` enum to categorize devices (StreamDeck, StreamDeckPedal, Generic)
- Created `OpenDeviceInfo` struct to track device state and button states
- Implemented report parsing for three device types:
  - Stream Deck: byte-per-button format with report ID prefix
  - Stream Deck Pedal: 3-button simple format
  - Generic: bitmap encoding (bit per button)
- Tracks previous button states to detect press/release transitions
- Generates `RawButtonEvent` structs for state changes
- Added comprehensive unit tests for:
  - Device type detection
  - Device info creation
  - Report parsing (Stream Deck, Pedal, Generic)
  - Multiple button simultaneous press
  - No-change detection (prevents duplicate events)
- Updated `mod.rs` to export `HidInputReader`, `HidDeviceType`, `OpenDeviceInfo`, `RawButtonEvent`

### Key Implementation Details:
- `READ_TIMEOUT_MS = 50`: Short timeout for responsive multi-device polling
- `POLL_INTERVAL_MS = 10`: Fast polling for low-latency input
- Device handles shared with `DefaultHidDeviceManager` via `Arc<Mutex<HashMap>>`
- Background task spawned via `tokio::spawn` with internal `spawn_blocking` for hidapi calls
- State machine pattern: only emits events on state transition (press or release)

## 2026-01-03 - Subtask 3.3 Complete: Audio and Fan System Integration

### Summary:
Verified and enhanced the audio control actions (volume, mute) and fan control actions
(speed, toggle) integration with their respective subsystems. The wiring was already
implemented in subtask 3.1, but this task added comprehensive tests to verify the
integration is working correctly.

### Acceptance Criteria Met:
- [x] VolumeUp/Down adjusts audio engine master volume (via set_volume)
- [x] MuteToggle toggles audio mute state (sets to 0 on mute, restores on unmute)
- [x] FanSpeedUp/Down adjusts fan controller speed (via set_speed)
- [x] FanToggle toggles fan on/off (speed 0 = off, current speed = on)
- [x] Graceful handling when MQTT not connected (MqttError -> ActionError::ExecutionFailed)

### Audio Integration Details:
- `execute_audio_action()` in executor.rs handles VolumeUp, VolumeDown, MuteToggle
- Internal volume state tracked in `volume_level: Arc<RwLock<u8>>` (default 80)
- Internal mute state tracked in `is_muted: Arc<RwLock<bool>>`
- Volume step: +/- 10, clamped to 0-100 range
- Calls `audio_engine.set_volume()` when engine is available
- Mute toggles between 0 and saved volume level

### Fan Integration Details:
- `execute_fan_action()` in executor.rs handles FanSpeedUp, FanSpeedDown, FanToggle
- Internal fan state tracked in `fan_speed` (default 50) and `fan_on` (default false)
- Requires both fan controller AND fan profile to be configured
- Speed step: +/- 10, clamped to 0-100 range
- Calls `fan_controller.set_speed(&profile_id, speed)` via async
- Errors (MqttError::NotConnected, etc.) gracefully converted to ActionError::ExecutionFailed
